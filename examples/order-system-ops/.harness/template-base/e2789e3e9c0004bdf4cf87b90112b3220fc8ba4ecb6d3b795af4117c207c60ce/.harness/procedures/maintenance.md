# モダナイズ後の継続保守

## 維持する知識
現在のInventory、承認Decision、依存グラフ、Behavior Contract、Deploymentを保守基盤にする。
Behavior Contractには、業務の入力・出力・制約について合意した振る舞いを記す。
Runごとの履歴を残し、最新表示を再構成できるようにする。

## 変更の入口
ソース・依存artifact・設定・DB schemaの変更、障害、サポート情報、脆弱性情報、テスト失敗、ADRとの乖離をChangeEventとして受け取る。
情報の出所と取得日を記録し、利用製品・実配備版と照合してから影響を判断する。
定期確認はopt-inの運用設定とし、対象、頻度、担当、権限、通知条件を設定して開始する。
今回のキットは定期実行を開始しない。

## 差分ループ
変更 → 影響分析 → stale Finding → 必要範囲の再調査 → Decision/Task更新 → 回帰検証 → 新Baseline承認とする。
新機能・不具合修正はBehavior Contractの意図差として理由と受入条件を記録する。
根拠が古いままの判断はレビュー対象として表示し、古い承認を新状態へ自動的に持ち越さない。

## 共通改善の反映
複数システムで繰り返した手順は配布テンプレートへ戻して改善する。
新しいテンプレートリリースは各system-opsに更新PRを作る契機とし、業務知識や設定の所有権を維持する。
テンプレート更新、アプリの更新、本番配備の承認は別の変更として扱う。

## 運用の確認項目
サポート期限、依存更新の滞留、再現可能な検証範囲、未解決リスク、失敗テスト、証跡の保持、復元訓練をレビューする。
KPIは成功件数だけでなく、合意した重要な振る舞いのうち確認できた範囲、判定不能の理由、根拠の鮮度、復旧可能性を含める。
