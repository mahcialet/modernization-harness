# テンプレートとしての版管理

## 決定
ハーネスrepo内の `templates/` を配布元とし、対象システムへ展開した後は独立Gitリポジトリで運用する。
配布版、導入版、個別変更を分けて追跡する。共通改善は新リリースとして提示し、各システムがレビューして取り込む。

## 版の役割
| 識別子 | 意味 |
|---|---|
| `VERSION` / `template_version` | 配布するテンプレートと設計キットの版 |
| `template-vX.Y.Z` | 配布元のリリースタグ規約。今回のZIP作成ではタグ未作成 |
| `schema_version` | 構造化成果物の互換性契約 |
| `runtime_version` | 将来の実行エンジン版。現段階は未実装 |
| repoのcommit / artifact digest | 調査・検証するアプリ構成 |
| `template_digest` | テンプレートmanifestと全配布ファイルの内容識別 |
| `base_dir` | 変数展開後に実際に適用した、三者比較の基準 |

0.xでは互換性に影響する変更をMINOR、文書訂正などをPATCHとして記録する。
1.x以降は破壊的変更をMAJORで示す運用へ移行する。schema更新は別途migration手順を持つ。
既存のrunは当時のschemaを保持し、新しい読み取り投影を生成する。

## ファイルの所有権
テンプレートmanifestの各ファイルには `managed` または `seed` を付ける。

- `managed`：共通指示・手順・標準設定。旧基準、導入先、新基準の三者比較対象。
- `seed`：system.yaml、環境定義、個別READMEなど。初期化後はシステム所有として保持する。
- manifestにないファイル：調査・ADR・Task・証跡などのシステム記録。更新対象外として扱う。

`managed`を編集した場合も導入先の変更を検知する。初版ツールでは両側変更を競合にして、作業者が採用結果を明示する。
`seed`の新しい記述例は差分レビューに表示し、既存内容は維持する。版が上がったことを、全seedが新雛形と同じという意味では扱わない。

## 導入時
`tools/template.py init` は新規または空のディレクトリへ展開する。
`.harness/template.lock.json` と `.harness/template-base/<digest>/` を同じコミットに含める。
lockにはテンプレートID、版、タグ規約、内容digest、変数、所有権、適用基準のhashを保存する。
配布元commitが未確定のローカルZIPでは `source_commit: null` を明記し、内容digestを識別根拠とする。

## 更新時
1. 対象リポジトリを清潔な作業状態にして、更新専用ブランチを作る。
2. 信頼できる新リリースを別ディレクトリへ展開し、チェックサムを確認する。
3. `plan` で旧基準・導入先・新基準を比較する。ネットワーク接続や外部コマンドは実行しない。
4. `review.md`、差分、seedの提案、schema変更を確認する。競合は `resolve` で採用ファイルを指定する。
5. 計画のSHA-256を確認し、`apply --approve <digest>` を実行する。
6. 適用前検査は計画後のファイル変更を検出する。変更があれば新しい計画を作る。
7. テストを実行し、共通ファイル・lock・新基準を同じPRでレビューする。

ツールは通常終了・検出可能な例外時の復旧を扱う。プロセス強制終了や電源断を含むファイルシステム全体のトランザクションは提供しないため、Gitブランチとコミットを復旧点にする。
承認用digestは計画とpayloadの整合性確認であり、本人認証・署名ではない。リリースの真正性は信頼する配布経路とGit署名等で別途確認する。

## 初回リリースの起点
本一式を最初の正式な配布版0.1.0として管理する。作成途中の仮の版番号は来歴資料に残し、正式な更新履歴と分ける。
初期の配布版・テンプレート版・スキーマ版はそれぞれ0.1.0。以後の更新では、配布内容とデータ契約の互換性を別々に評価する。

## 旧草案からの導入
初期のbootstrap資料は配布lockを持たない。今回のZIPを新しい配布元として置き、旧資料に加えた独自変更を比較して取り込む。
実際に過去に適用した基準が不明な場合は、その基準を推定して自動更新する代わりに、新しい差分レビューで初期登録する。

草案版で既に導入先を生成した場合は、元のlock・基準・調査記録を履歴として保存し、新規ディレクトリに0.1.0の雛形を生成して独自変更を比較する。
採用する設定や記録は明示的なレビューを経て取り込み、移した構造化記録を新しいスキーマで検証する。
これは正式な版管理を開始するための初期登録として扱う。通常の更新ツールが旧版指定を拒否する安全策はそのまま維持する。

## 配布元のリリース
`VERSION`、各 `template.json`、CHANGELOG、schema互換性表、サンプルを更新し、検証を通す。
初回はローカルで `git init`、レビュー後のcommit、`git tag -a template-v0.1.0 -m ...` を作り、必要に応じてリモートへ公開する。
GitHubのTemplate機能は初期コピーに使えるが、生成repoは独自の履歴で始まるため、継続更新はこのlockと差分手順で扱う。[R1]
`git merge-file` は三者のテキストを使ったマージに利用できる。競合解消の補助として使い、採用結果を本ツールのresolveに渡せる。[R2]

詳細なコマンドは `docs/getting-started.md` に記載する。
