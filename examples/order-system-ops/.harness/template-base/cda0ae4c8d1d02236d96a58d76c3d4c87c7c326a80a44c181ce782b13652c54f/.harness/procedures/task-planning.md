# 調査からタスク分解へ

## 入力の確定
人が承認したInventory、残るUnknown、依存グラフ、業務の重要度を入力とする。
移行方式が未決定の領域には、調査・PoC・Decision作成タスクを用意する。
移行先の決定前に実装内容を断定する代わりに、判断に必要な情報と受入条件を先に揃える。

## 作業の階層
WorkstreamはDI・Web・DB・認証・実行基盤などの責務単位で管理する。
Taskはレビュー可能な成果の単位とし、対象repo、変更範囲、開始条件、完了条件、比較シナリオ、復旧方法を持つ。
ExecPlanは複数Taskの進め方と判断履歴を説明する。機械的な依存関係の正本はTaskデータとする。

## Taskに含める内容
目的、根拠Finding、承認Decision、対象repoとbase SHA、依存Task、必要能力、変更する契約、受入テスト、成果物、承認範囲、リスク、復旧点を記録する。
状態変更とgit merge、アプリの配布・本番切替は別のイベントとして追跡する。

## 横断変更の例
共通JARの互換版公開 → Webの移植 → Batchの移植 → 混在組合せ検証 → EC2検証 → 段階切替とする。
ただし互換APIを先に作れるならWebとBatchの実装は並列化し、それぞれ検証済みの版をlockで固定する。
複数repoのPRはChangeSet IDで束ね、マージ条件、成果物hash、配布順序、混在時の安全条件を明記する。
複数repoのcommitを同時に更新する操作を、業務状態まで原子的に切り替える仕組みとは区別する。

## 完了判定
依存Taskの完了、対象Decisionの有効性、Snapshot一致、受入検証、未解決差分、承認対象digestを確認する。
テストがあるだけでは完了にせず、実行結果と観測範囲を保存する。
本番への切替にはスキーマ変更・バックアップ・復元可能性の独立した確認を加える。
