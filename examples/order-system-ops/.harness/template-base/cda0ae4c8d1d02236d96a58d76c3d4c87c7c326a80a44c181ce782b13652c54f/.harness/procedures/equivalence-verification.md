# 新旧アプリケーションの同等性検証

## 判定の意味
「同じ」とする対象は、承認した業務契約について、指定した入力・初期状態・観測範囲で振る舞いが同等であること。
有限のテスト結果と、全入力に対する完全な同一性を区別する。
旧アプリの不具合やセキュリティ上の問題は、意図的変更のDecisionと受入テストで扱う。

## 比較手順
1. System Snapshotと新旧・混在構成を確定し、環境準備の妥当性を確認する。
2. 同じ論理内容のDB、ファイル、queue、stub状態を、新旧それぞれの独立領域へ復元する。
3. 時刻、timezone、locale、文字コード、乱数、採番の条件を揃えるか、差分の意味をルール化する。
4. 同じ業務シナリオを実行し、HTTP、DOM、DB差分、ファイル、イベント、外部送信を収集する。
5. 非同期処理には完了条件とtimeoutを持ち、収束を確認してから比較する。
6. 生観測を保持し、版付きの正規化規則を別適用して差分と結果を保存する。
7. 未検証範囲、例外条件、残存リスクを含むレポートをレビューする。

## 観測対象
ステータス・ヘッダー・本文、画面遷移・フォーム・セッション、計算・境界値、行の追加更新削除、制約、トランザクション境界、外部送信回数と順序、バッチ再実行を対象とする。
金銭・在庫・権限は不変条件を別に定義し、ロールバック、競合更新、重複実行、timeout、リトライを検証する。
共通DBを使うアプリ群は、同時実行と共有テーブルの不変条件もシステム横断で確認する。

## 正規化
IDは参照整合性を保った写像で対応付ける。全IDを削除する処理は、関連付けの回帰を観測できなくするため採用結果をレビューする。
順序を整列して比較するのは順序に意味がない契約に限定する。
時刻は絶対時刻・相対間隔・業務日付を区別し、重要な期限や更新順序を残す。
各ルールは理由、適用scope、テスト、承認を持ち、正常化前の出力を再確認できるようにする。

## 結果
- `equivalent`：指定観測範囲で一致。
- `accepted_difference`：厳密な条件と有効な承認に一致する意図差。
- `regression`：契約に対する想定外の差分。
- `inconclusive`：初期状態、観測、環境などの不足で判断が成立していない。

AcceptedDifferenceには対象Scenario、JSON path等の差分条件、旧値・新値またはpredicate、理由、Decision、承認者、期限・見直し日を持たせる。
広い正規化規則で新たな差分を隠す代わりに、差分ごとに業務意味を判断する。
性能は同等性とは別のSLO・測定条件・繰返し回数で評価し、EC2の実配置条件も検証する。

## 継続保守
移行完了後は、承認済み契約とfixturesを回帰基準として保持する。
旧ランタイムの稼働継続に依存せず、契約、重要な観測、テストを新しい基準として維持する。
