# 独立調査と一括照合

## 目的と入力
まず現状だけを調査し、調査結果をレビューしてから移行方式を決める。
同一System Snapshot、共通質問票、対象範囲、出力する項目と形式の取り決めをA・B・Cへ渡す。
全員が共通して確認する項目は、アプリ境界、主要処理経路、トランザクション、認証、他repoとの境界、共有DB、実行時前提、未確認事項である。

下表は各Agentの重点を示す。A・B・Cは表に挙げた領域に加え、上記の共通項目も確認する。

| Agent | 重点 | 独立に確認する共通領域 |
|---|---|---|
| A | アプリ構造、DI/AOP、Seasar2固有機能 | TX、認証、アプリ間通信、起動点 |
| B | Java/Tomcat/OS、依存JAR、配置・運用 | DB接続、共通JAR、cron、実行時設定 |
| C | 業務処理、SQL、入力出力、副作用 | TX境界、共有テーブル、外部通知、検証可能性 |
| D | 全報告の一次情報照合 | 不一致、欠落、宣言と観測の差、Coverage |

## 独立性の実装
別セッション、別context、別作業領域、別出力領域を使う。
調査中の許可入力は固定ソース、承認した共通資料、本人用指示とする。他Agentの出力はDの入力パッケージで初めて集約する。
共有ユーザー設定、MCP、他セッション履歴、環境変数による入力混入もmanifestへ記録し、必要に応じて無効化・隔離する。
プロンプトの指示は補助とし、実際の読取範囲をプロセスまたはコンテナのアクセス制御で実装する。
A/B/Cに異なるモデルを使う選択肢は持つが、モデル差を必須条件にはしない。

## 複数repoの進め方
各Agentは全システムの入口・出口と共通の重要境界を確認する。
大きいrepoの詳細調査は自分の配下に分割し、その配下同士の情報共有は同じ調査系列として記録する。
別系列A/B/Cの途中報告を共有する構成とは区別する。
呼出元設定、呼出先経路、JAR座標、DB接続先、ファイルパス、スケジュールを対応付け、独立調査後に横断グラフへ統合する。

## 出力
Claim/EvidenceのJSON、読みやすい日本語報告、Coverage表、Unknown一覧を出す。
Coverageは `confirmed / investigated-no-evidence / not-inspected / blocked` を使う。
見つからなかった機能は、調べたパス・条件と探索限界を記録して表す。

## 合流と失敗時
3系列の成功したAttemptについて、出力を確定して以後変更しない状態にしてからDを起動する。
失敗系列は同じ入力で再試行し、Attempt IDを追加する。入力を変える場合は新Snapshotで全系列の比較条件を揃える。
部分結果を出す場合は `partial` とし、不足系列と未確認範囲を明示した承認待ち資料にする。

## Dの判定
`confirmed / conflicting / unverified / missing` で主張を対応付ける。
同じ主張を3名が繰り返しても、根拠の強さは一次情報で評価する。
異なる環境・版・処理経路の差は、単純な矛盾と混同せずscopeを分割する。
解消できない相違には、追加調査方法、必要権限、影響する移行判断を付ける。
