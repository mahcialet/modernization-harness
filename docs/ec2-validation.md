# 実EC2への接続と最終検証

## 検証の段階
L1は承認したHTTPS操作、L2は配備・設定・ログ・プロセスの観測、L3は隔離された検証EC2で状態変化を含む比較を行う。
コンテナとEC2では、同じScenarioと観測対象・収集方法の取り決めを使う。環境による差をFindingとして記録する。
HTTP GETやログ読取でも、負荷・監査記録・アクセス時刻・キャッシュ等への影響を評価する。

## 接続準備
SSMが利用できる環境ではSession Manager等を候補とする。SSM Agent、OS対応、IAM、ネットワーク、pluginの条件を実対象で確認する。[R5]
AL1/古いAgentでの可用性を前提にせず、既存の承認済み経路か隔離cloneで観測する。
SSHとSSMは輸送方式であり、それ自体でアプリを読み取り専用にするものではない。

## 安全な実行境界
観測用、隔離検証用、環境作成用、切替用の権限を分ける。
任意shellの許可より、引数を検査する名前付きcollector・SSM document・限定OSユーザーを優先する。
Providerが接続先ID、操作内容、影響、出力先、承認期限を検証してから実行する。
本番は既定でobserveのみを提供し、reset/seed/障害注入は隔離環境の能力として宣言する。

## 証跡
account、region、instance ID、AMI、architecture、kernel、OS、JDK、Tomcat、実配備WAR/JARのhash、設定digest、実行時刻を取得可能範囲で記録する。
取得できない情報は未確認として理由を残す。環境のdesired stateと観測stateを分ける。
SSMのSSH・port forwardingセッションではセッション内容のロギングに制約があるため、接続記録に加えてアプリ側とcollector側の観測証跡を保存する。[R5]

## 隔離検証
検証用EC2、DB、queue、storage、メール・決済などの送信先を個別に分離する。
本番と同じ初期DBを使う場合は必要な承認とマスキングを行い、検証側に本番書込権限が届かない接続設定を確認する。
IAM/SGだけでなくアプリ設定と認証情報のscopeも検査する。

## 切替と復旧
新旧・混在構成、canaryの切替条件、業務SLO、schema互換期間、復旧可能なデータ状態を確認する。
アプリを旧版へ戻す手順と、変更済みDBを復旧する手順を分ける。不可逆なschema/data変更には別の復元計画を設ける。
本番承認は対象環境・成果物・時間帯・手順digestに結び付け、検証用の承認を本番へ流用しない。
